🗄️ O que é SGBD Relacional?

Antes de tudo, vamos entender o básico: o que é um banco de dados e o que é um SGBD?

📚 Conceitos Fundamentais

📦
Banco de Dados Coleção organizada de dados armazenados eletronicamente
🖥️
SGBD Sistema Gerenciador de Banco de Dados — o software que gerencia o banco
🔗
Relacional Dados organizados em tabelas com relações entre elas

💡 Analogia para Fixar

📚 Pense assim:
  • Banco de Dados = Uma biblioteca (onde os livros ficam guardados)
  • SGBD = O bibliotecário (organiza, busca e cuida dos livros)
  • Tabelas = As estantes da biblioteca
  • Registros = Os livros em cada estante

🏆 Vantagens dos SGBDs Relacionais

✅ Vantagens

  • ✅ Integridade dos dados
  • ✅ Consistência transacional
  • ✅ Estrutura organizada
  • ✅ Relacionamentos claros
  • ✅ Linguagem SQL padronizada
  • ✅ Segurança e backups

📊 Tabelas e Registros

No banco de dados relacional, os dados são organizados em tabelas. Vamos entender a estrutura!

📐 Estrutura de uma Tabela

Uma tabela é composta por:

  • Colunas (campos/atributos) — Definem o tipo de dado (nome, idade, email)
  • Linhas (registros/tuplas) — São os dados em si (João, 25, joao@email.com)

💡 Regra importante: Cada linha (registro) em uma tabela deve ser única. É por isso que usamos a chave primária!

📦 Entidades e Atributos

Vamos aprofundar nos dois elementos mais importantes do diagrama ER!

🏢 O que é uma Entidade?

Uma entidade representa algo do mundo real que queremos armazenar no banco de dados. Pode ser:

  • Tangível: Cliente, Produto, Pedido, Funcionário
  • Intangível: Conta bancária, Curso, Matrícula
🎯 Como identificar entidades?

Pergunte: "O que meu sistema precisa armazenar?" Cada resposta é uma entidade potencial!

🏷️ O que são Atributos?

Atributos são as características ou propriedades de uma entidade.

🎯 Identificando Entidades em um Caso Real

Caso: TechSolutions - Empresa de TI

🏢 Entidades identificadas

  • CLIENTE — Quem contrata os serviços
  • FORNECEDOR — Quem fornece produtos
  • PRODUTO — O que é vendido
  • VENDA — Transações realizadas
  • FUNCIONÁRIO — Quem trabalha na empresa

📋 Atributos de cada entidade

Cada entidade tem seus próprios atributos específicos. Por exemplo, CLIENTE tem nome, CPF, email; PRODUTO tem nome, preço, estoque.

⚠️ Cuidado: Nem tudo que parece entidade é! "Endereço" pode ser um atributo de CLIENTE ou uma entidade separada, dependendo do contexto.

🔀 Relacionamentos entre Entidades

As entidades não existem isoladas — elas se conectam! Esses conectores são os relacionamentos.

🔗 O que é um Relacionamento?

É uma associação entre duas ou mais entidades. Representa como os dados se conectam no mundo real.

📊 Tipos de Cardinalidade

A cardinalidade indica quantas instâncias de uma entidade podem se relacionar com outra.

1️⃣
1:1 (Um para Um)

Um registro de A se relaciona com apenas um de B.

Ex: Pessoa ↔ CPF

🔀
1:N (Um para Muitos)

Um registro de A se relaciona com vários de B.

Ex: Cliente ↔ Pedidos

🌐
N:M (Muitos para Muitos)

Vários registros de A se relacionam com vários de B.

Ex: Alunos ↔ Disciplinas

📋 Exemplos Práticos

🔹 Relacionamento 1:1

Exemplo: Um USUÁRIO tem apenas um PERFIL, e um PERFIL pertence a apenas um USUÁRIO.

🔹 Relacionamento 1:N (mais comum!)

Exemplo: Um CLIENTE pode fazer vários PEDIDOS, mas cada PEDIDO é de apenas um CLIENTE.
CLIENTE
🔑 id_cliente

🔹 Relacionamento N:M

Exemplo: Um ALUNO cursa várias DISCIPLINAS, e uma DISCIPLINA tem vários ALUNOS.

⚠️ Atenção: Relacionamentos N:M precisam de uma tabela intermediária no banco!

📐 Tabela Intermediária

Quando temos um relacionamento N:M, criamos uma terceira tabela para "quebrar" o relacionamento em dois 1:N.

💡 Regra de ouro: Na implementação física, só existem relacionamentos 1:N. Relacionamentos N:M são sempre convertidos em dois 1:N com uma tabela intermediária!

🔑 Chave Primária (Primary Key)

A chave primária é um dos conceitos mais importantes do banco de dados relacional!

🎯 O que é uma Chave Primária?

É um campo (ou conjunto de campos) que identifica unicamente cada registro em uma tabela.

🎯 Características da Chave Primária:
  • ✅ Única — Não pode haver dois registros com a mesma PK
  • ✅ Não nula — Todo registro deve ter uma PK (NOT NULL)
  • ✅ Imutável — Idealmente, não deve mudar
  • ✅ Mínima — Usar o menor número possível de campos

📋 Exemplo Prático

📋 tabela: clientes
🔑 id (PK)
nome
cpf
email
1
João Silva
123.456.789-00
joao@email.com
2
Maria Santos
987.654.321-00
maria@email.com

🔢 Tipos de Chave Primária

🔢
Surrogate (Artificial)

Criada pelo sistema (id auto-incremento)

Ex: id INT AUTO_INCREMENT

🆔
Natural

Usa um dado real do negócio

Ex: CPF, email, código do produto

🔗
Composta

Combinação de 2 ou mais campos

Ex: (id_pedido, id_produto)

💻 Criando Chave Primária em SQL

-- Chave primária simples com auto-incremento CREATE TABLE clientes ( id INT PRIMARY KEY AUTO_INCREMENT, nome VARCHAR(100) NOT NULL, email VARCHAR(150) );📋
-- Chave primária composta CREATE TABLE itens_pedido ( id_pedido INT, id_produto INT, quantidade INT, PRIMARY KEY (id_pedido, id_produto) );📋
-- Adicionando PK em tabela existente ALTER TABLE clientes ADD PRIMARY KEY (id);📋
⚠️ Recomendação: Use sempre uma chave surrogate (id auto-incremento) como PK. É mais simples, eficiente e evita problemas com mudanças de dados do negócio.

🌐 Chave Estrangeira (Foreign Key)

A chave estrangeira é o que conecta as tabelas, criando os relacionamentos!

🎯 O que é uma Chave Estrangeira?

É um campo em uma tabela que aponta para a chave primária de outra tabela. Ela cria o relacionamento entre as duas.

🎯 Função da FK:
  • 🔗 Conectar tabelas — Cria o relacionamento
  • 🛡️ Garantir integridade — Só aceita valores válidos
  • 📊 Permitir JOINs — Consultas entre tabelas

🛡️ Ações em Cascata

O que acontece quando o registro referenciado é alterado ou excluído?

AçãoComportamentoExemplo
CASCADE Aplica a mesma ação Se deleta cliente, deleta pedidos
SET NULL Coloca NULL na FK Se deleta cliente, pedido fica sem cliente
RESTRICT Bloqueia a ação (padrão) Não deixa deletar cliente com pedidos
NO ACTION Semelhante ao RESTRICT Não permite ação
FOREIGN KEY (id_cliente) REFERENCES clientes(id) ON DELETE CASCADE ON UPDATE CASCADE📋
💡 Dica: Use CASCADE com cuidado! Pode apagar muitos dados sem querer. Em muitos casos, RESTRICT é mais seguro.

🛡️ Integridade Referencial

A integridade referencial garante que os relacionamentos entre tabelas sejam consistentes.

🎯 O que é Integridade Referencial?

É a garantia de que não existem registros órfãos — ou seja, toda FK deve apontar para um registro existente na tabela referenciada.

🛡️ Exemplo:

Se um PEDIDO tem id_cliente = 5, DEVE existir um cliente com id=5 na tabela clientes. Não pode existir pedido sem cliente!

📊 Benefícios

✅
Consistência Dados sempre válidos e coerentes
🛡️
Segurança Evita dados órfãos e inválidos
🔒
Confiabilidade Pode confiar nos relacionamentos
⚡
Performance Consultas JOIN mais eficientes

🔄 Regras ao Atualizar ou Excluir

🗑️ Ao EXCLUIR um registro referenciado ▼

O que acontece com os registros que apontam para ele?

  • RESTRICT (padrão): Bloqueia a exclusão
  • CASCADE: Exclui também os registros relacionados
  • SET NULL: Coloca NULL nas FKs relacionadas
✏️ Ao ATUALIZAR a PK referenciada ▼

O que acontece com as FKs que apontam para ela?

  • RESTRICT (padrão): Bloqueia a atualização
  • CASCADE: Atualiza também as FKs
  • SET NULL: Coloca NULL nas FKs

💻 Exemplo Completo

CREATE TABLE pedidos ( id INT PRIMARY KEY AUTO_INCREMENT, id_cliente INT NOT NULL, data_pedido DATE, valor_total DECIMAL(10,2), FOREIGN KEY (id_cliente) REFERENCES clientes(id) ON DELETE RESTRICT ON UPDATE CASCADE );📋
• Se tentar deletar cliente com pedidos → ERRO
• Se mudar id do cliente → pedidos são atualizados automaticamente
⚠️ Cuidado com CASCADE!

Usar CASCADE pode apagar muitos dados sem querer. Em sistemas reais, prefira RESTRICT e faça exclusões lógicas (soft delete) quando possível.

📐 Normalização de Banco de Dados

A normalização é o processo de organizar os dados para evitar redundâncias e inconsistências.

🎯 O que é Normalização?

É um conjunto de regras que ajudam a estruturar o banco de dados de forma eficiente, eliminando:

  • ❌ Redundância — Dados repetidos
  • ❌ Anomalias — Problemas ao inserir, atualizar ou excluir
  • ❌ Inconsistências — Dados conflitantes

  • 🔴 Anomalia de atualização: Se João mudar de cidade, precisa atualizar várias linhas
  • 🔴 Anomalia de exclusão: Se apagar venda 1, perde dados de João
  • 🔴 Anomalia de inserção: Não pode cadastrar cliente sem venda

📊 As Formas Normais

Existem várias "formas normais" (FN), cada uma com regras específicas:

1️⃣
1FN Atomicidade — valores atômicos
2️⃣
2FN Elimina dependências parciais
3️⃣
3FN Elimina dependências transitivas
🔟
FNBC Forma Normal de Boyce-Codd (avançada)
💡 Regra prática: Na maioria dos sistemas, chegar à 3FN é suficiente. Formas mais avançadas são usadas em casos específicos.

🎯 Benefícios da Normalização

  • ✅ Menos espaço em disco (sem redundância)
  • ✅ Atualizações mais rápidas (menos dados)
  • ✅ Consistência garantida
  • ✅ Mais flexibilidade para mudanças
  • ✅ Facilidade de manutenção

1️⃣ Primeira Forma Normal (1FN)

A 1FN é o primeiro passo da normalização. Ela garante que todos os valores sejam atômicos.

🎯 Regra da 1FN

📐 Regra: Todos os atributos devem conter apenas um valor por célula (valor atômico). Não pode haver grupos de atributos repetidos ou listas.

🛠️ Como Aplicar a 1FN

1️⃣ Identificar atributos multivalorados

Procure campos com listas ou múltiplos valores (telefones, emails, endereços)

2️⃣ Criar nova tabela

Para cada atributo multivalorado, crie uma tabela separada

3️⃣ Adicionar FK

Na nova tabela, adicione uma FK apontando para a tabela original

4️⃣ Verificar atomicidade

Garanta que cada célula tem apenas um valor

💡 Dica: A 1FN é o mínimo necessário para um banco relacional. Se sua tabela não está em 1FN, ela não é verdadeiramente relacional!

2️⃣ Segunda Forma Normal (2FN)

A 2FN elimina dependências parciais — quando um atributo depende apenas de parte da chave primária.

🎯 Regra da 2FN

📐 Regra: Estar em 1FN + todos os atributos não-chave devem depender completamente da chave primária inteira.

🔑 Quando se aplica?

A 2FN só faz sentido quando a chave primária é composta (tem mais de um campo).

3️⃣ Terceira Forma Normal (3FN)

A 3FN elimina dependências transitivas — quando um atributo depende de outro atributo que não é chave.

🎯 Regra da 3FN

📐 Regra: Estar em 2FN + nenhum atributo não-chave pode depender de outro atributo não-chave. Todos devem depender diretamente da chave primária.
💡 Lema da 3FN: "Cada atributo deve depender da chave, de toda a chave, e de nada mais além da chave."

4️⃣ Criar FKs

🔍 SQL - SELECT (Consultar)

O comando SELECT é o mais usado no SQL! Serve para consultar dados do banco.

🔹 Limitar resultados

SELECT * FROM clientes LIMIT 10;📋

✏️ SQL - UPDATE (Atualizar)

O comando UPDATE modifica registros existentes em uma tabela.

📐 Sintaxe Básica

UPDATE tabela SET coluna1 = valor1, coluna2 = valor2 WHERE condição;📋
⚠️ MUITO CUIDADO!

Se você esquecer o WHERE, TODOS os registros serão atualizados! Isso pode ser desastroso!

📋 Exemplos Práticos

🔹 Atualizar um registro específico

UPDATE clientes SET email = 'novo@email.com' WHERE id = 1;📋
Muda o email do cliente com id=1

🔹 Atualizar vários campos

UPDATE clientes SET nome = 'João Silva Jr.', cidade = 'Campinas' WHERE id = 1;📋

🔹 Atualizar vários registros

UPDATE produtos SET preco = preco * 1.10 WHERE categoria = 'Eletrônicos';📋
Aumenta em 10% o preço de todos os eletrônicos

🔹 Atualizar com base em outra tabela

UPDATE pedidos p JOIN clientes c ON p.id_cliente = c.id SET p.status = 'VIP' WHERE c.total_compras > 1000;📋
Marca como VIP pedidos de clientes que compraram mais de 1000

🛡️ Boas Práticas

🔍
Sempre use WHERE Evite atualizar tudo sem querer
🧪
Teste com SELECT antes Execute o WHERE como SELECT para ver o que será afetado
💾
Faça backup Antes de UPDATEs em produção
🔢
Use LIMIT Para limitar quantos registros serão afetados

💡 Técnica Segura

Antes de fazer UPDATE, teste o WHERE com SELECT:

-- 1. Teste primeiro: SELECT * FROM clientes WHERE cidade = 'São Paulo'; -- 2. Se estiver correto, faça o UPDATE: UPDATE clientes SET status = 'SP' WHERE cidade = 'São Paulo';📋

🗑️ SQL - DELETE (Excluir)

O comando DELETE remove registros de uma tabela.

📐 Sintaxe Básica

DELETE FROM tabela WHERE condição;📋
⚠️ EXTREMO CUIDADO!

DELETE sem WHERE apaga TODOS os registros da tabela! A ação é irreversível (sem backup)!

📋 Exemplos Práticos

🔹 Excluir um registro específico

DELETE FROM clientes WHERE id = 5;📋
Remove o cliente com id=5

🔹 Excluir vários registros

DELETE FROM pedidos WHERE status = 'cancelado';📋
Remove todos os pedidos cancelados

🔹 Excluir com condição composta

DELETE FROM clientes WHERE cidade = 'São Paulo' AND data_cadastro < '2020-01-01';📋
Remove clientes de SP cadastrados antes de 2020

🔹 Excluir todos os registros (CUIDADO!)

DELETE FROM clientes;📋
⚠️ Apaga TODOS os clientes! Use com extrema cautela!

🛡️ Alternativa: Soft Delete

Em vez de excluir, marque o registro como "inativo":

-- Em vez de: DELETE FROM clientes WHERE id = 5; -- Use: UPDATE clientes SET ativo = FALSE WHERE id = 5;📋

🔗 SQL - JOIN (Juntar Tabelas)

O JOIN combina dados de duas ou mais tabelas baseado em um relacionamento.

🎯 Por que usar JOIN?

Em bancos normalizados, os dados estão em tabelas separadas. O JOIN permite consultá-los juntos!

📐 Sintaxe Básica

SELECT colunas FROM tabela1 JOIN tabela2 ON tabela1.coluna = tabela2.coluna;📋

📊 Tipos de JOIN

⚫
INNER JOIN

Retorna apenas registros que têm correspondência em AMBAS as tabelas

🔵
LEFT JOIN

Retorna todos da tabela esquerda + correspondências da direita

🟢
RIGHT JOIN

Retorna todos da tabela direita + correspondências da esquerda

🟡
FULL JOIN

Retorna todos os registros de ambas as tabelas

📋 Exemplos Práticos

🔹 INNER JOIN — Pedidos com dados do cliente

SELECT p.id_pedido, c.nome, p.valor_total FROM pedidos p INNER JOIN clientes c ON p.id_cliente = c.id;📋
Mostra apenas pedidos que têm cliente válido

🔹 LEFT JOIN — Todos os clientes, mesmo sem pedidos

SELECT c.nome, p.id_pedido, p.valor_total FROM clientes c LEFT JOIN pedidos p ON c.id = p.id_cliente;📋
Mostra todos os clientes, mesmo os que não têm pedidos (valor NULL)

🔹 JOIN com 3 tabelas

SELECT c.nome, p.id_pedido, pr.nome as produto, ip.quantidade FROM clientes c JOIN pedidos p ON c.id = p.id_cliente JOIN itens_pedido ip ON p.id_pedido = ip.id_pedido JOIN produtos pr ON ip.id_produto = pr.id;📋
Consulta completa: cliente, pedido, produto e quantidade

📊 Comparação Visual dos JOINs

TipoRetornaQuando usar
INNER JOIN Só correspondências Quando quer apenas registros relacionados
LEFT JOIN Todos da esquerda + matches Quando quer todos da tabela principal
RIGHT JOIN Todos da direita + matches Raramente usado (pode inverter e usar LEFT)
FULL JOIN Todos de ambas Quando quer tudo, independente de match

💡 Apelidos (Aliases)

Use apelidos para deixar o código mais limpo:

SELECT c.nome AS cliente, p.valor AS total FROM clientes AS c JOIN pedidos AS p ON c.id = p.id_cliente;📋
💡 Dica: Use aliases curtos (c, p, u) para facilitar a leitura. A maioria dos desenvolvedores usa a primeira letra da tabela!

1. (Dissertativa) Explique o que é normalização e por que é importante em um banco de dados.

Resposta sugerida: Normalização é o processo de organizar os dados em um banco de dados relacional para reduzir redundâncias e evitar inconsistências. É importante porque: (1) elimina dados repetidos, economizando espaço; (2) evita anomalias de inserção, atualização e exclusão; (3) garante consistência dos dados; (4) facilita a manutenção; (5) melhora o desempenho das consultas. As formas normais (1FN, 2FN, 3FN) são regras progressivas que ajudam a estruturar o banco de forma eficiente.

2. (Dissertativa) Explique a diferença entre chave primária e chave estrangeira, dando exemplos.

Resposta sugerida: A chave primária (PK) é um campo que identifica UNICAMENTE cada registro em uma tabela. Ela não pode ser NULL nem repetida. Exemplo: na tabela CLIENTES, o campo "id_cliente" é a PK. Já a chave estrangeira (FK) é um campo que referencia a PK de outra tabela, criando um relacionamento entre elas. Exemplo: na tabela PEDIDOS, o campo "id_cliente" é uma FK que aponta para a PK da tabela CLIENTES. A PK garante unicidade dentro da tabela, enquanto a FK garante integridade referencial entre tabelas.
